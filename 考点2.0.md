## 0. 出题风格总结

这门考试的风格非常明显：

1. **不是纯背概念**，而是给一个场景/代码，让你指出 OS 原理问题。
2. **同步与线程安全几乎必考**，但外壳代码每年会变。
3. **调度和内存管理常以场景题出现**，要求你解释为什么某策略适合/不适合。
4. **kernel / interrupt / system call 常以简答题穿插**。
5. **PPT 图示内容通常不会让你背细节数值，而是考图背后的原则**。
6. **代码题里有一部分是纯 C memory/pointer bug**，这些不全来自七份 OS PPT；本预测只重点覆盖从 PPT 能推出的 OS 考点。

<a id="1-最高优先级考点-synchronisation-concurrency"></a>
# 1. 最高优先级考点：Synchronisation / Concurrency

预测等级：`⭐⭐⭐⭐⭐`

原因：

- 七份课件中 `os_06_sync.pdf` 内容最多、最完整。
- 三份试卷都反复考线程安全、race condition、critical section、mutex、parallelism。
- 外壳代码会变化，但核心永远是 shared data + interleaving + lock placement。

---

<a id="1-1-必考概念-race-condition"></a>
## 1.1 必考概念：Race Condition

你必须会答：

```text
A race condition occurs when the correctness of a program depends on the timing or interleaving of concurrent operations on shared data.
```

中文模板：

```text
Race condition 是多个线程/进程并发访问共享变量，并且至少一个会修改它，导致最终结果依赖执行交错顺序，从而可能出现不可预测或错误结果。
```

典型题型：

- 给 `count++` / `count--`。
- 给 stack `push/pop`。
- 给 queue `producer/consumer`。
- 给 booking/reservation 系统。
- 问哪些变量是 shared data，哪些地方是 critical section。

你要写出的点：

1. 哪些变量共享：比如 `count`, `requests[]`, `allSeats[]`, `noOfMealsAvailable`。
2. 哪些操作不是 atomic：比如 check-then-act、increment/decrement、array write + count update。
3. 可能出现什么错误：lost update、duplicate booking、overflow/underflow、inconsistent state。

---

<a id="1-2-必考概念-critical-section"></a>
## 1.2 必考概念：Critical Section

标准答案：

```text
A critical section is a part of code where shared data or shared resources are accessed or modified, and which must not be executed concurrently by multiple threads if doing so can produce inconsistent state.
```

中文：

```text
Critical section 是访问或修改共享资源的代码区域。如果多个线程同时执行这段代码，可能导致共享状态不一致，所以需要 mutual exclusion 保护。
```

常见考法：

- “What is a critical section?”
- “Why is this code not thread-safe?”
- “Where would you lock/unlock?”

---

<a id="1-3-必考-mutex-放哪里"></a>
## 1.3 必考：Mutex 放哪里？

核心原则：

```text
Lock only the shared state, not the whole function unnecessarily.
```

如果题目说：

> Your solution should maximise the degree of possible parallelism.

那么你应该：

- 把 thread-safe 的慢函数放锁外。
- 把 shared array / shared count 的修改放锁内。
- 不要把 `get()` 或 `handle()` 这种题目明确说 thread-safe 的函数锁住。

典型 producer-consumer 修正思路：

```c
void producer() {
    unsigned int r = get();        // get() thread-safe, outside lock

    pthread_mutex_lock(&m);
    if (request_count < 8) {
        requests[request_count] = r;
        request_count++;
    }
    pthread_mutex_unlock(&m);
}

void consumer() {
    unsigned int r;
    int has_item = 0;

    pthread_mutex_lock(&m);
    if (request_count > 0) {
        request_count--;
        r = requests[request_count];
        has_item = 1;
    }
    pthread_mutex_unlock(&m);

    if (has_item) {
        handle(r);                // handle() thread-safe, outside lock
    }
}
```

注意：如果题目强调 “get() 一旦调用，结果必须插入 buffer”，而 buffer 满了不能丢，则需要 condition variable 或 semaphore，让 producer 等待 not_full。

---

<a id="1-4-高概率-producer-consumer-bounded-buffer"></a>
## 1.4 高概率：Producer-Consumer / Bounded Buffer

预测原因：

- PPT 重点讲 producer-consumer。
- 考试很喜欢把它包装成 queue、requests、server、booking。

必须会写 condition variable 版本：

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;

void producer() {
    unsigned int r = get();

    pthread_mutex_lock(&m);
    while (request_count == 8) {
        pthread_cond_wait(&not_full, &m);
    }

    requests[request_count++] = r;

    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&m);
}

void consumer() {
    unsigned int r;

    pthread_mutex_lock(&m);
    while (request_count == 0) {
        pthread_cond_wait(&not_empty, &m);
    }

    r = requests[--request_count];

    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&m);

    handle(r);
}
```

解释点：

- `not_full`：producer 等 buffer 有空位。
- `not_empty`：consumer 等 buffer 有 item。
- `while` 而不是 `if`：被唤醒后要重新检查条件。
- `pthread_cond_wait` 会 atomically release mutex and sleep，醒来后 reacquire mutex。

---

<a id="1-5-高概率-semaphore-版本"></a>
## 1.5 高概率：Semaphore 版本

PPT 中 semaphore 是核心内容，所以可能考概念或伪代码。

Bounded buffer semaphore 模板：

```c
semaphore mutex = 1;
semaphore empty = N;
semaphore full = 0;

producer:
    wait(empty);
    wait(mutex);
    insert_item();
    signal(mutex);
    signal(full);

consumer:
    wait(full);
    wait(mutex);
    remove_item();
    signal(mutex);
    signal(empty);
```

必解释：

- `mutex` protects buffer。
- `empty` counts empty slots。
- `full` counts available items。

---

<a id="1-6-高概率-为什么同步-bug-难找"></a>
## 1.6 高概率：为什么同步 bug 难找？

答题模板：

```text
Synchronisation errors are difficult to find because they depend on rare timing-dependent interleavings. The program may work correctly in most executions and fail only under specific scheduling orders, CPU speeds, loads or compiler optimisations. Adding debugging output may also change timing and hide the bug.
```

中文：

```text
同步错误难找，因为它不是每次都会出现，而是依赖线程执行顺序。调试时加 printf 还可能改变 timing，把 bug 隐藏掉。
```

<a id="2-最高优先级考点-scheduling-场景分析"></a>
# 2. 最高优先级考点：Scheduling 场景分析

预测等级：`⭐⭐⭐⭐⭐`

原因：

- 调度课件非常适合出应用题。
- 试卷常给 server/editor/compiler/verification program 等场景。
- 考法不是让你背算法，而是让你判断策略适不适合。

---

<a id="2-1-必会-scheduling-criteria"></a>
## 2.1 必会：Scheduling Criteria

考试答场景题前，先判断目标：

| 场景 | 最重要 criteria |
|---|---|
| editor / GUI / interactive app | response time |
| web preview request | response time |
| background image rendering | throughput / CPU utilisation |
| verification program | CPU utilisation，不能影响交互任务 |
| overloaded multi-user system | response time + throughput + avoid thrashing |

五个 criteria：

```text
CPU utilisation, throughput, turnaround time, waiting time, response time
```

---

<a id="2-2-必会-fcfs"></a>
## 2.2 必会：FCFS

优点：

- simple。
- low overhead。

缺点：

- non-preemptive。
- long CPU-bound job can block short/interactive jobs。
- bad response time。

场景判断：

如果题目说：

> editor should be responsive at all times

那 FCFS 通常不适合。

---

<a id="2-3-必会-round-robin"></a>
## 2.3 必会：Round Robin

优点：

- fair。
- suitable for time-sharing。
- better response than FCFS。

缺点：

- quantum too small → too many context switches。
- quantum too large → behaves like FCFS。
- 不区分任务重要性。

考试答题句：

```text
Round Robin improves responsiveness because each ready process receives a time slice, but the time quantum must be chosen carefully: too small causes excessive context-switch overhead, too large allows CPU-bound processes to monopolise the CPU.
```

---

<a id="2-4-必会-priority-scheduling"></a>
## 2.4 必会：Priority Scheduling

优点：

- high-priority interactive tasks can respond quickly。
- suitable when some tasks are more important。

缺点：

- starvation of low-priority processes。

解决：

- ageing。

考试场景模板：

```text
Use preemptive priority scheduling. Give the editor or interactive requests high priority, I/O-heavy compiler medium priority, and long CPU-intensive verification or rendering jobs lower priority. Use ageing to avoid starvation of low-priority jobs.
```

---

<a id="2-5-高概率-是否需要-preemption"></a>
## 2.5 高概率：是否需要 preemption？

如果题目问：

> Is there a suitable scheduling strategy without pre-emption?

答案大概率：

- 如果要求 editor always responsive，non-preemptive 很难保证。
- 因为 CPU-bound job 可能长时间不释放 CPU。
- 需要 preemption 才能强制拿回 CPU 给 interactive task。

模板：

```text
Without preemption, a CPU-intensive process may keep the CPU until it blocks or terminates, so an interactive editor cannot be guaranteed to remain responsive. A preemptive strategy is needed so that the OS can interrupt long CPU bursts and schedule the editor quickly.
```

---

<a id="2-6-高概率-cpu-bound-vs-i-o-bound-场景"></a>
## 2.6 高概率：CPU-bound vs I/O-bound 场景

判断方法：

- CPU-intensive：long CPU bursts。
- I/O-intensive：frequent I/O waits。
- interactive：short bursts, response time important。

如果系统中有：

1. verification program：CPU-intensive + memory-heavy。
2. compiler：CPU + I/O intensive。
3. editor：not CPU-intensive, little memory, must be responsive。

推荐：

- preemptive priority / multilevel queue。
- editor high priority。
- compiler medium。
- verification low/background。
- ageing to avoid starvation。

# 3. 最高优先级考点：Memory Management

预测等级：`⭐⭐⭐⭐⭐`

原因：

- 试卷多次考 paging/segmentation/page replacement/thrashing。
- memory 课件结构很清楚，适合出简答 + 小计算。

---

<a id="3-1-必会-paging-vs-segmentation"></a>
## 3.1 必会：Paging vs Segmentation

标准答案：

```text
Paging divides memory into fixed-size pages and frames, mainly to simplify allocation and avoid external fragmentation. Segmentation divides memory according to the logical structure of a program, such as code, data and stack, with variable-sized segments.
```

中文：

```text
Paging 是按固定大小切，主要为了内存分配方便；Segmentation 是按程序逻辑结构切，例如代码段、数据段、栈段。
```

常见小问：

- paging 是否避免 external fragmentation？是。
- segmentation 是否固定大小？不是。
- segmentation 为什么适合 sharing/protection？因为 code/data/stack 的逻辑边界清楚。

---

<a id="3-2-必会-virtual-memory-demand-paging"></a>
## 3.2 必会：Virtual Memory / Demand Paging

核心：

- logical memory 与 physical memory 分离。
- 程序可以拥有大虚拟地址空间。
- 只有需要的 pages 才加载进 RAM。

page fault 答题模板：

```text
A page fault occurs when a process accesses a page that is not currently in physical memory. The OS must locate the page on disk, bring it into a free frame or replace another page, update the page table, and restart the instruction.
```

---

<a id="3-3-必会-page-replacement-algorithms"></a>
## 3.3 必会：Page Replacement Algorithms

### FIFO

可能考计算表。

规则：

- 替换最早进入内存的 page。

优点：简单。

缺点：不考虑 locality，可能 Belady's anomaly。

### Optimal

规则：

- 替换未来最晚使用或不再使用的 page。

特点：

- 理论最优。
- 不可实现。
- 用作 benchmark。

### LRU

规则：

- 替换最久没有被使用的 page。

特点：

- 利用 locality。
- 需要硬件/记录支持。

### Second Chance

规则：

- FIFO + reference bit。
- bit=1：清零，给第二次机会。
- bit=0：替换。

---

<a id="3-4-高概率-thrashing-判断"></a>
## 3.4 高概率：Thrashing 判断

标准解释：

```text
Thrashing occurs when processes do not have enough frames and spend most of their time paging pages in and out instead of executing useful instructions.
```

判断：

| 现象 | 说明 |
|---|---|
| page fault rate very high | thrashing strong signal |
| disk activity high | 因为频繁换页 |
| CPU utilisation low | CPU 在等 disk |
| throughput low | 进程完成少 |
| response time high | 用户体验差 |

和其他情况区分：

```text
If CPU utilisation is close to 100% and disk activity is normal, the CPU may be overloaded. If disk activity is high but page fault rate is not, disk I/O may be overloaded. If page fault rate and disk activity are both high while CPU utilisation drops, thrashing is likely.
```

---

<a id="3-5-高概率-swapping-策略"></a>
## 3.5 高概率：Swapping 策略

如果问：内存满了要 swap out 谁？

原则：

1. swap out low-priority process。
2. swap out blocked/waiting process if safe。
3. avoid swapping out interactive process。
4. consider memory size and pending I/O。
5. 目标是 maximize CPU utilisation and minimize response time。

答题模板：

```text
A good choice is to swap out a low-priority or blocked background process rather than an interactive process, because this preserves responsiveness. The OS should also consider the size of the process and whether it has pending I/O, since swapping a large process is expensive and pending I/O may complicate relocation.
```

# 4. 高优先级考点：Process / Thread / Context Switch

预测等级：`⭐⭐⭐⭐`

原因：

- 每年可能穿插 4-8 分简答。

---

<a id="4-1-process-定义"></a>
## 4.1 Process 定义

```text
A process is a program in execution.
```

包含：

- program code/text
- PC
- registers
- stack
- heap
- data section
- open files

---

<a id="4-2-process-states"></a>
## 4.2 Process States

必须会：

```text
new, ready, running, waiting, terminated
```

状态转换：

- ready → running：scheduler dispatch。
- running → ready：preemption/time slice expired。
- running → waiting：I/O or event wait。
- waiting → ready：I/O completion。
- running → terminated：exit。

---

<a id="4-3-pcb"></a>
## 4.3 PCB

PCB 保存 OS 管理/恢复进程所需信息：

- process state
- pid
- program counter
- CPU registers
- scheduling info
- memory management info
- accounting info
- I/O status
- open files

---

<a id="4-4-context-switch"></a>
## 4.4 Context Switch

标准答案：

```text
A context switch is the operation of saving the state of the currently running process or thread and restoring the state of another one so that the CPU can switch execution.
```

步骤：

1. save current PC/registers。
2. update current PCB。
3. select next process。
4. load next PCB state。
5. restore registers/PC。
6. resume execution。

为什么不能太多？

```text
Because context switching is overhead. The CPU spends time saving/restoring state instead of executing useful work, and cache/TLB locality may be reduced.
```

---

<a id="4-5-every-program-has-at-least-one-thread"></a>
## 4.5 Every program has at least one thread?

答案：是。

解释：

```text
A running program is a process, and execution requires at least one thread of control. Even if the programmer does not explicitly create additional threads, the process has a main thread executing the program.
```

中文：

一个程序运行起来至少要有一条执行路径，也就是 main thread。

<a id="5-1-system-call"></a>
## 5.1 System Call

必须准确表达：

```text
A system call is the controlled interface through which a user program requests a service from the kernel.
```

常见例子：

- read
- write
- open
- close
- fork
- exec

不要混淆：

- `printf()` 是 library function。
- 底层可能调用 `write()` system call。

---

<a id="5-2-user-space-kernel-space"></a>
## 5.2 User Space / Kernel Space

重点：

- user program 不能直接访问 kernel memory。
- kernel 不能盲信 user pointer。
- 需要 `copy_to_user` / `copy_from_user`。

可能考法：

> Why can kernel code not directly use a user-space pointer?

模板：

```text
Because a user-space pointer may be invalid, malicious, or refer to memory not safely accessible in kernel mode. The kernel must use checked copy functions such as copy_from_user and copy_to_user to transfer data safely across the user-kernel boundary.
```

---

<a id="5-3-process-context-vs-interrupt-context"></a>
## 5.3 Process Context vs Interrupt Context

| Context | 能 sleep 吗 | 能访问 user data 吗 | 例子 |
|---|---|---|---|
| process context | 可以，在合适情况下 | 可以通过 copy functions | system call |
| interrupt context | 不可以 | 一般不可以 | device interrupt handler |

高概率问题：

> Can an interrupt handler store data directly in a user process’s memory?

答案：不能直接。

原因：

- interrupt handler 不在该 user process 的 process context 中。
- interrupt context must not sleep。
- 应该先写 kernel buffer，再 wake up relevant process。

---

<a id="5-4-mutex-semaphore-vs-spinlock-in-kernel"></a>
## 5.4 Mutex/Semaphore vs Spinlock in Kernel

必会判断：

- process context only：mutex/semaphore okay。
- interrupt context possible：spinlock。
- critical section long：avoid spinlock if possible。
- critical section short and cannot sleep：spinlock。

答题模板：

```text
A mutex or semaphore may put the caller to sleep, so it is only suitable when the critical section is executed in process context. A spinlock uses busy waiting and can be used in interrupt context, but the critical section must be kept short to avoid wasting CPU time.
```

<a id="8-不要过拟合但应该掌握的代码类考法"></a>
# 8. 不要过拟合但应该掌握的代码类考法

这里不是预测具体代码，而是预测代码背后的知识点。

---

<a id="8-1-check-then-act-race"></a>
## 8.1 Check-then-act Race

典型模式：

```c
if (count < SIZE) {
    array[count] = x;
    count++;
}
```

问题：

- 两个线程可能同时看到 `count < SIZE`。
- 同时写同一个 slot。
- count update lost。
- 甚至 overflow。

修正：

```c
pthread_mutex_lock(&m);
if (count < SIZE) {
    array[count] = x;
    count++;
}
pthread_mutex_unlock(&m);
```

如果不能丢任务，则用 condition variable 等待。

---

<a id="8-2-return-before-unlock"></a>
## 8.2 Return Before Unlock

典型错误：

```c
pthread_mutex_lock(&m);
if (count == 0) {
    return -1;
}
pthread_mutex_unlock(&m);
```

问题：

- return 前没 unlock。
- 其他线程永远拿不到锁。
- deadlock-like situation。

修正：

```c
pthread_mutex_lock(&m);
if (count == 0) {
    pthread_mutex_unlock(&m);
    return -1;
}
pthread_mutex_unlock(&m);
```

---

<a id="8-3-different-locks-protecting-same-shared-data"></a>
## 8.3 Different Locks Protecting Same Shared Data

错误：

```c
push uses m1;
pop uses m2;
```

如果它们都访问 `count` 和 `values[]`，那必须用同一把锁。

原因：

- mutual exclusion 是针对 shared resource 的。
- 两把不同锁不能互斥彼此。

---

<a id="8-4-lock-granularity"></a>
## 8.4 Lock Granularity

如果一个操作只读共享数据，可考虑 read-write lock。

例子：

- `listAllBookings()` 只读 booking array。
- `reserveSeatMeal()` 会写。

为了 maximize parallelism：

- 多个 readers 可以同时进入。
- writer 独占。
