## 0. 三年真题整体规律

### 0.1 最高频主题

三年题的核心方向非常集中：

| 高频主题 | 出现方式 | 你要会什么 |
|---|---|---|
| C memory bugs | 代码找错、修代码 | `malloc/calloc/free`、dangling pointer、use-after-free、buffer overflow、array越界、recursive free |
| Concurrency | 多线程代码找race condition | mutex、critical section、read/write lock、最大化parallelism |
| Scheduling | 场景题 | FCFS、Round Robin、Priority、pre-emption、interactive responsiveness |
| Memory management | 理论题 + 算法题 | paging vs segmentation、FIFO page replacement、swapping、thrashing |
| Kernel / System call | 场景 + 代码题 | user space / kernel space、system call、interrupt handler、device driver、critical section in kernel |

### 0.2 考试出题风格

这门考试不是只考定义，它很喜欢这样问：

1. 给你一段 C code，说它 compiles but does not work as intended，让你找 bugs。
2. 给你一个 multi-threaded server 场景，让你指出 race conditions 并修正。
3. 给你一个现实场景，比如 editor 要 responsive、compiler 用很多 I/O、verification program CPU-intensive，让你选 scheduling / memory strategy。
4. 给你 kernel / device driver code，让你同时考虑 memory、concurrency、user/kernel boundary。
5. 给你 page reference string，让你手算 FIFO page replacement。

所以复习时不要只背概念，要背 **问题模式 + 答题句式 + 修正代码模板**。

## 1. C Memory Bugs 必考模板

### 1.1 常见 memory bug 清单

考试里看到 C code，优先检查下面这些：

| Bug | 中文理解 | 常见后果 |
|---|---|---|
| Buffer overflow | 写超出数组边界 | 覆盖其他变量、crash、security vulnerability |
| Use-after-free | `free(p)` 后继续用 `p` | undefined behaviour、crash、数据损坏 |
| Double free | 同一个地址 `free` 两次 | heap corruption、crash |
| Memory leak | `malloc/calloc` 后没有 `free` | 长时间运行程序内存越来越多 |
| Dangling pointer | 指针指向已经无效的内存 | 读写随机数据、crash |
| Returning address of local variable | 返回 stack 局部变量地址 | 函数结束后地址失效 |
| Freeing non-heap memory | `free` 一个不是 malloc/calloc/realloc 得来的地址 | undefined behaviour |
| Missing NULL check | 没检查 `malloc/calloc` 是否返回 `NULL` | 之后 dereference 导致 crash |
| Out-of-bounds access | 数组下标越界 | undefined behaviour |
| Wrong free order | 先 `free(node)` 再访问 `node->next` | use-after-free |

### 1.2 标准答题模板：array out of bounds

题目常问：Give two possible consequences of access beyond array boundaries.

可以答：

```text
Accessing beyond the boundary of an array in C causes undefined behaviour. Possible consequences include:
1. The program may crash, for example with a segmentation fault.
2. It may silently corrupt nearby memory, overwriting other variables or control data.
3. It may appear to work sometimes, which is dangerous because the bug becomes hard to reproduce.
4. It may create security vulnerabilities, such as buffer overflow attacks.
```

中文理解：C 不帮你检查数组越界，你访问错地方后，可能马上崩，也可能不崩但偷偷把别的数据改坏。

### 1.3 `strcpy` 高频陷阱

`strcpy(dest, src)` 会把 `src` 的所有字符，包括最后的 `'\0'`，复制到 `dest`。它不会检查 `dest` 够不够大，也不会自动分配内存。

危险写法：

```c
#define BUFFERLENGTH 80

struct entry_t {
    int entry_id;
    char title[BUFFERLENGTH];
};

strcpy(newItem.entry.title, newTitle);
```

如果 `newTitle` 长度超过 79 个字符，`title` 放不下，因为还要留一个位置给 `'\0'`，就会 buffer overflow。

修法 1：限制长度。

```c
strncpy(newItem->entry.title, newTitle, BUFFERLENGTH - 1);
newItem->entry.title[BUFFERLENGTH - 1] = '\0';
```

修法 2：如果题目说 string arbitrary length，最好动态分配。

```c
newItem->entry.title = malloc(strlen(newTitle) + 1);
if (newItem->entry.title == NULL) {
    // handle allocation failure
}
strcpy(newItem->entry.title, newTitle);
```

注意：如果 struct 里是 `char title[80]`，那它是 fixed-size array，不能直接让它指向 malloc 出来的内存。要动态长度就应该把字段改成：

```c
char *title;
```

### 1.4 `free` 的顺序

错误写法：

```c
free(items);
items = items->next;
```

这里 `items` 已经被 free 了，再访问 `items->next` 就是 use-after-free。

正确写法：

```c
while (items != NULL) {
    struct list_t *next = items->next;
    free(items);
    items = next;
}
```

如果 node 里面还有动态分配的字段，比如 `char *title`，要先 free 内部字段，再 free node：

```c
while (items != NULL) {
    struct list_t *next = items->next;
    free(items->entry.title);
    free(items);
    items = next;
}
```

### 1.5 Binary tree recursive free 高频题

危险写法：

```c
void deleteNode(treeNode_t *node) {
    if (node != 0) {
        free(node->value);
        free(node);
    }

    deleteNode(node->left);
    deleteNode(node->right);
}
```

问题：

1. `value` 是 `int`，不是 pointer，不能 `free(node->value)`。
2. `free(node)` 后还访问 `node->left` 和 `node->right`，这是 use-after-free。
3. 如果 `node == NULL`，后面仍然会访问 `node->left`，直接 crash。
4. 正确顺序应该是先递归释放 children，再释放自己。

正确写法：

```c
void deleteNode(treeNode_t *node) {
    if (node == NULL) {
        return;
    }

    deleteNode(node->left);
    deleteNode(node->right);

    free(node);
}
```

如果 node 里有 heap-allocated 字段，才需要额外 free 那些字段。

## 2. Pointer / Array / Struct / Linked List / Tree 找错题

### 2.1 Pointer 是什么

标准答案：

```text
A pointer is a variable that stores the memory address of another object or function. In C, pointers can be dereferenced to access or modify the value stored at that address.
```

中文：pointer 不是数据本身，而是“数据的地址”。`p = &x` 表示 p 里存的是 x 的地址；`*p` 表示通过地址找到 x 本人。

### 2.2 Pointer 如何让函数返回多个值

C 函数本身只能 `return` 一个值，但可以通过 pointer 参数修改外部变量。

```c
void divmod(int a, int b, int *quotient, int *remainder) {
    *quotient = a / b;
    *remainder = a % b;
}

int main() {
    int q, r;
    divmod(17, 5, &q, &r);
    printf("%d %d\n", q, r);
}
```

答题句式：

```text
A function can return several values by taking pointer parameters. The caller passes the addresses of variables, and the function writes results through these pointers.
```

### 2.3 Struct 作为参数：传值 vs 传地址

传值：

```c
void changeAge(struct Student s) {
    s.age = 30;
}
```

这只改 copy，不改原来的 `Student`。

传地址：

```c
void changeAge(struct Student *s) {
    s->age = 30;
}
```

`->` 等价于 `(*s).age`。

考试里如果函数想改外部结构体，通常要用 pointer。

### 2.4 Linked list 插入题常见错误

看 linked list 插入题时，检查：

1. 新 node 是否用 `malloc` / `calloc` 分配在 heap 上。
2. 有没有把 local variable 的地址放进 list。
3. 有没有处理 empty list。
4. 有没有处理插入到 head 前面。
5. while loop 是否更新了 `currentItem`。
6. `prevItem` 是否可能 uninitialised。
7. `next` pointer 是否正确连接。
8. 如果有动态字符串，是否分配并释放。

错误示例：

```c
struct list_t newItem;
prevItem->next = &newItem;
return allItems;
```

`newItem` 是局部变量，在函数结束后消失，list 里留下 dangling pointer。

正确思路：

```c
struct list_t *newItem = malloc(sizeof(struct list_t));
if (newItem == NULL) {
    return allItems; // or handle error
}
```

### 2.5 Ordered linked list 插入模板

```c
struct list_t *addElem(struct list_t *allItems, int newID, const char *newTitle) {
    struct list_t *newItem = malloc(sizeof(struct list_t));
    if (newItem == NULL) {
        return allItems;
    }

    newItem->entry.entry_id = newID;
    strncpy(newItem->entry.title, newTitle, BUFFERLENGTH - 1);
    newItem->entry.title[BUFFERLENGTH - 1] = '\0';

    if (allItems == NULL || allItems->entry.entry_id >= newID) {
        newItem->next = allItems;
        return newItem;
    }

    struct list_t *current = allItems;
    while (current->next != NULL && current->next->entry.entry_id < newID) {
        current = current->next;
    }

    newItem->next = current->next;
    current->next = newItem;

    return allItems;
}
```

如果题目要求 `newTitle` arbitrary length，就需要把 `title` 改为 `char *title`，然后：

```c
newItem->entry.title = malloc(strlen(newTitle) + 1);
strcpy(newItem->entry.title, newTitle);
```

### 2.6 Priority queue enqueue 模板

题目要求：priority queue 是 singly linked list，high priority values in front，相同 priority 保持 FIFO。

核心逻辑：

1. 如果 queue empty，直接插入。
2. 如果新 node priority 比 head 高，插到最前。
3. 否则向后找位置。
4. 对于相同 priority，为了 FIFO，新来的要放在同 priority 的后面，所以 while 条件应该允许 `>=` 或者根据写法保留同优先级在前。

模板：

```c
int enqueue(NODE **queue, NODE *p) {
    if (queue == NULL || p == NULL) {
        return -1;
    }

    if (*queue == NULL || p->priority > (*queue)->priority) {
        p->next = *queue;
        *queue = p;
        return 0;
    }

    NODE *q = *queue;

    while (q->next != NULL && q->next->priority >= p->priority) {
        q = q->next;
    }

    p->next = q->next;
    q->next = p;

    return 0;
}
```

解释句式：

```text
The list is kept in descending priority order. The loop skips all existing nodes with priority greater than or equal to the new node's priority, so nodes with the same priority remain before the new node, preserving FIFO order among equal priorities.
```

## 3. Undefined Behaviour 答题模板

### 3.1 Undefined behaviour 是什么

标准答案：

```text
Undefined behaviour means that the C standard imposes no requirements on what the program does. The program may crash, produce incorrect results, appear to work, or behave differently on another compiler, optimisation level, or machine.
```

中文：Undefined behaviour 不是“报错”的意思，而是“C 语言标准不保证会发生什么”。最可怕的是它可能看起来正常，但其实已经错了。

### 3.2 为什么危险

答题模板：

```text
Undefined behaviour is dangerous because it makes the program unpredictable and non-portable. The compiler may assume undefined behaviour never occurs and perform optimisations based on that assumption, which can lead to surprising results. Such bugs are also hard to test and reproduce because the same code may behave differently depending on the environment.
```

中文背法：

1. 不可预测。
2. 不可移植。
3. 编译器优化可能让结果更奇怪。
4. 很难 debug。
5. 可能造成安全漏洞。

### 3.3 高频 UB 例子

```c
int a[10];
a[10] = 5;          // out-of-bounds

int *p = malloc(4);
free(p);
*p = 10;            // use-after-free

int x = 10;
free(&x);           // freeing stack memory

int *f() {
    int x = 10;
    return &x;      // returning address of local variable
}
```

## 4. Threads and Race Conditions

### 4.1 Every program has at least one thread?

答案：Yes。

```text
Yes. Even if a program does not explicitly create threads, it has at least one thread of execution, usually called the main thread. The program's main function runs in this thread.
```

中文：你没写 `pthread_create`，程序也至少有一个 main thread，因为 `main()` 总要有东西在跑。

### 4.2 Race condition 是什么

```text
A race condition occurs when the correctness of a program depends on the relative timing or interleaving of multiple threads accessing shared data, and at least one of the accesses is a write.
```

中文：多个线程同时碰同一个共享数据，并且至少有人在写，结果取决于谁先谁后，这就是 race condition。

### 4.3 为什么 synchronisation errors 难找

答题模板：

```text
Synchronisation errors are difficult to find because they depend on particular thread interleavings, timing, scheduling decisions and hardware behaviour. The bug may occur rarely and may disappear when debugging or adding print statements, because these actions change timing.
```

中文：

1. 只有某些线程交错顺序才会触发。
2. 很难稳定复现。
3. 加 `printf` 或 debug 反而改变 timing。
4. 在一台机器上不出错，换机器可能出错。

### 4.4 经典错误：把循环变量地址传给多个线程

错误代码逻辑：

```c
for (i = 1; i < 11; i++) {
    pthread_create(&tid, NULL, myfunc, &i);
}
```

所有 threads 拿到的是同一个 `i` 的地址。线程真正执行时，`i` 可能已经变了，所以输出可能重复、跳号、甚至都接近最终值。

修法 1：每个 thread 一个独立参数数组。

```c
pthread_t tids[10];
int args[10];

for (int i = 0; i < 10; i++) {
    args[i] = i + 1;
    pthread_create(&tids[i], NULL, myfunc, &args[i]);
}

for (int i = 0; i < 10; i++) {
    pthread_join(tids[i], NULL);
}
```

修法 2：动态分配参数，在线程里 free。

```c
for (int i = 1; i <= 10; i++) {
    int *arg = malloc(sizeof(int));
    *arg = i;
    pthread_create(&tids[i - 1], NULL, myfunc, arg);
}

void *myfunc(void *arg) {
    int i = *((int *)arg);
    free(arg);
    printf("%d ", i);
    return NULL;
}
```

### 4.5 为什么要 `pthread_join`

如果 main thread 创建完子线程后直接结束，整个进程可能结束，其他线程还没来得及打印或执行完。所以通常要：

```c
pthread_join(tid, NULL);
```

## 5. Mutex / Critical Section / Condition Variable

### 5.1 Critical section 是什么

```text
A critical section is a part of a program that accesses shared resources and must not be executed by more than one thread at the same time, otherwise race conditions may occur.
```

中文：critical section 就是“访问共享资源的危险区域”。这段代码同一时间只能一个线程进去。

### 5.2 Mutex 基本模板

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

pthread_mutex_lock(&m);

// critical section: access shared data

pthread_mutex_unlock(&m);
```

### 5.3 加锁范围原则

加锁范围不能太小，也不能太大。

| 加锁范围 | 问题 |
|---|---|
| 太小 | 共享数据还没保护完整，仍然 race condition |
| 太大 | 并发度差，很多不冲突操作也被迫等待 |

考试经常要求：Your solution should maximise the degree of possible parallelism. 这句话的意思是：不要一把大锁锁全世界，要根据数据冲突范围设计锁。

### 5.4 Condition variable 标准逻辑

Condition variable 要和 mutex 一起用。

```c
pthread_mutex_lock(&mutex);

while (condition_is_false) {
    pthread_cond_wait(&cond, &mutex);
}

use_shared_data();

pthread_mutex_unlock(&mutex);
```

producer:

```c
pthread_mutex_lock(&mutex);

make_condition_true();

pthread_cond_signal(&cond);

pthread_mutex_unlock(&mutex);
```

重点：

1. `pthread_cond_wait(&cond, &mutex)` 会自动释放 mutex，然后睡眠。
2. 被 signal 唤醒后，会重新拿到 mutex 才继续。
3. 必须用 `while`，不要用 `if`，因为可能 spurious wakeup，或者醒来后条件又被其他线程改了。

### 5.5 什么时候用 read/write lock

如果数据结构读多写少，用 read/write lock 比 mutex 更好。

```c
pthread_rwlock_rdlock(&lock);
// read-only operation
pthread_rwlock_unlock(&lock);

pthread_rwlock_wrlock(&lock);
// write operation
pthread_rwlock_unlock(&lock);
```

规则：

- 多个 reader 可以同时读。
- writer 必须独占。
- 如果有 writer 正在写，reader 和其他 writer 都要等。

适合题型：listAllBookings 只读，reserveSeatMeal 会写；member 只读，insert/delete 会写。

## 6. Thread-safe Data Structure 常见写法

### 6.1 Stack thread-unsafe 题

原始问题：

```c
int count;
double values[STACK_SIZE];

void push(double v) {
    values[count++] = v;
}

double pop() {
    return values[--count];
}

int is_empty() {
    return count == 0;
}
```

问题：

1. `count++` 和 `--count` 不是 atomic。
2. `push` 和 `pop` 同时操作 `count`，会造成 lost update。
3. 两个 `push` 同时执行，可能写到同一个 index。
4. `is_empty` 读 `count` 时，其他线程可能正在改 `count`。
5. 没检查 overflow / underflow。

### 6.2 错误加锁方案：两个 mutex

错误：

```c
pthread_mutex_t m1;
pthread_mutex_t m2;

push uses m1;
pop uses m2;
is_empty uses m1;
```

问题：`push` 和 `pop` 仍然可以同时修改 `count`，因为它们用的是不同锁。保护同一个共享变量必须用同一把锁。

另一个 bug：

```c
int is_empty() {
    pthread_mutex_lock(&m1);
    return count == 0;
    pthread_mutex_unlock(&m1);
}
```

`return` 在 unlock 前面，所以 unlock 永远执行不到，造成 deadlock。

### 6.3 Thread-safe stack 模板

```c
#define STACK_SIZE 20

int count = 0;
double values[STACK_SIZE];
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

int push(double v) {
    pthread_mutex_lock(&m);

    if (count == STACK_SIZE) {
        pthread_mutex_unlock(&m);
        return -1;
    }

    values[count++] = v;

    pthread_mutex_unlock(&m);
    return 0;
}

int pop(double *out) {
    pthread_mutex_lock(&m);

    if (count == 0) {
        pthread_mutex_unlock(&m);
        return -1;
    }

    *out = values[--count];

    pthread_mutex_unlock(&m);
    return 0;
}

int is_empty() {
    pthread_mutex_lock(&m);

    int result = (count == 0);

    pthread_mutex_unlock(&m);
    return result;
}
```

### 6.4 Producer-consumer queue 题

原始问题：

```c
unsigned int request_count = 0;
unsigned int requests[8];

void producer() {
    if (request_count < 8) {
        requests[request_count] = get();
        request_count++;
    }
}

void consumer() {
    if (request_count > 0) {
        request_count--;
        handle(requests[request_count]);
    }
}
```

问题：

1. `request_count` shared 且被多个线程读写。
2. producer 可能同时写同一个 slot。
3. consumer 可能和 producer 同时改 `request_count`。
4. check-then-act race：检查 `request_count < 8` 后，真正写入前可能已经被其他 producer 改了。
5. 如果 `get()` 的结果必须插入，不能在队列满时直接丢弃，应该等待或重试。
6. 为最大化 parallelism，`get()` 和 `handle()` 如果是 thread-safe 且不访问共享 queue，应该放在 lock 外面。

### 6.5 Producer-consumer with mutex：最大化 parallelism 模板

只用 mutex 且题目没要求 condition variable 时，可以这样：

```c
void producer() {
    unsigned int r = get();

    while (1) {
        pthread_mutex_lock(&m);

        if (request_count < 8) {
            requests[request_count] = r;
            request_count++;
            pthread_mutex_unlock(&m);
            break;
        }

        pthread_mutex_unlock(&m);
        // queue full: retry later, or yield/sleep depending on allowed functions
    }
}

void consumer() {
    unsigned int r;
    int has_request = 0;

    pthread_mutex_lock(&m);

    if (request_count > 0) {
        request_count--;
        r = requests[request_count];
        has_request = 1;
    }

    pthread_mutex_unlock(&m);

    if (has_request) {
        handle(r);
    }
}
```

解释：

- `get()` 放 lock 外，因为它可能慢，而且 thread-safe。
- `handle()` 放 lock 外，因为处理请求不需要占着 queue lock。
- lock 只保护 `request_count` 和 `requests[]` 的修改。
- 这样 parallelism 更高。

如果允许 condition variables，更理想：

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_full = PTHREAD_COND_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;

void producer() {
    unsigned int r = get();

    pthread_mutex_lock(&m);

    while (request_count == 8) {
        pthread_cond_wait(&not_full, &m);
    }

    requests[request_count++] = r;

    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&m);
}

void consumer() {
    pthread_mutex_lock(&m);

    while (request_count == 0) {
        pthread_cond_wait(&not_empty, &m);
    }

    unsigned int r = requests[--request_count];

    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&m);

    handle(r);
}
```

### 6.6 Seat booking concurrency 题

场景：`allSeats[]` 存座位是否 available，是否 meal booked；`noOfMealsAvailable` 存剩余餐数。`reserveSeatMeal` 会修改 seats 和 meal count；`listAllBookings` 只读。

问题：

1. 两个 threads 可能同时看到同一个 seat available，然后都 reserve。
2. 两个 threads 可能同时看到 `noOfMealsAvailable > 0`，导致超卖 meals。
3. `listAllBookings` 读的时候，另一个 thread 正在改，可能看到 inconsistent state，比如 seat booked 但 meal flag 还没改完。
4. 如果用一把 mutex 全锁，可以正确但并发度低。
5. 更好的方法：read/write lock。reserve 用 write lock；list 用 read lock。多个 list 可以并发，reserve 独占。

模板：

```c
pthread_rwlock_t booking_lock = PTHREAD_RWLOCK_INITIALIZER;

int reserveSeatMeal(bool wantsMeal) {
    pthread_rwlock_wrlock(&booking_lock);

    for (int i = 0; i < SEATS_AVAILABLE; i++) {
        if (allSeats[i].available) {
            if (wantsMeal) {
                if (noOfMealsAvailable > 0) {
                    allSeats[i].available = false;
                    allSeats[i].meal_booked = true;
                    noOfMealsAvailable--;
                    pthread_rwlock_unlock(&booking_lock);
                    return i;
                }
            } else {
                allSeats[i].available = false;
                allSeats[i].meal_booked = false;
                pthread_rwlock_unlock(&booking_lock);
                return i;
            }
        }
    }

    pthread_rwlock_unlock(&booking_lock);
    return -1;
}

void listAllBookings() {
    pthread_rwlock_rdlock(&booking_lock);

    for (int i = 0; i < SEATS_AVAILABLE; i++) {
        if (!allSeats[i].available) {
            printf("Seat %d booked\n", i);
            if (allSeats[i].meal_booked) {
                printf("Meal for seat %d booked\n", i);
            }
        }
    }

    pthread_rwlock_unlock(&booking_lock);
}
```

## 7. Scheduling 策略题

### 7.1 Scheduling 题常见关键词

| 关键词 | 暗示 |
|---|---|
| CPU-intensive | CPU burst 长，容易霸占 CPU |
| I/O-intensive | 经常 block 等 I/O |
| Interactive / responsive | 需要短 response time |
| Background | 可以低优先级 |
| Highly loaded | 调度策略更重要 |
| Pre-emption | OS 可以打断正在运行的 process |
| Throughput | 单位时间完成多少工作 |
| Response time | 用户发出请求到获得响应的时间 |

### 7.2 FCFS

First-Come-First-Served，谁先来谁先跑，不抢占。

优点：

- 简单。
- overhead 小。
- 适合 batch jobs。

缺点：

- convoy effect：一个长 CPU job 在前面，后面短任务全等。
- interactive response time 差。
- 不适合需要 responsiveness 的系统。

答题句式：

```text
FCFS may lead to poor response time because a long CPU-bound job can keep the CPU for a long time while short interactive or I/O-bound jobs wait behind it.
```

### 7.3 Round Robin

每个 process 分一个 time quantum，时间到了就 preempt。

优点：

- 公平。
- interactive response time 比 FCFS 好。
- 不会让一个 CPU-bound job 长时间霸占 CPU。

缺点：

- quantum 太小：context switch overhead 大。
- quantum 太大：接近 FCFS。
- 不区分重要程度。

答题句式：

```text
Round Robin is suitable for time-sharing systems because each runnable process receives the CPU regularly. However, too small a time quantum causes too many context switches, while too large a quantum behaves similarly to FCFS.
```

### 7.4 Priority Scheduling

给不同 process 不同优先级，高优先级先跑。

适合：

- interactive editor 高优先级。
- purchase requests 高优先级。
- background image rendering 低优先级。
- verification program CPU-intensive 可以低优先级。

风险：

- starvation：低优先级可能长期拿不到 CPU。
- 需要 aging 防止饿死。

答题句式：

```text
Priority scheduling is suitable when some tasks are more urgent than others, for example interactive requests. To avoid starvation of low-priority jobs, ageing can gradually increase the priority of waiting processes.
```

### 7.5 Pre-emption 为什么重要

没有 pre-emption 的策略很难保证 responsiveness。因为如果 CPU-intensive process 一直运行，editor 或 interactive process 只能等它主动让出 CPU。

答题模板：

```text
Without pre-emption, the operating system cannot force a long-running CPU-bound process to give up the CPU. Therefore, an interactive editor may become unresponsive if a CPU-intensive verification program keeps running. A responsive system needs pre-emptive scheduling so that high-priority interactive tasks can run promptly.
```

### 7.6 场景题：editor + compiler + verification program

题目场景：

- Verification program：CPU-intensive，可能跑几小时，用大量 memory。
- Model compiler：CPU-intensive，也用很多 I/O，不太占 memory，还要访问远程 server library。
- Editor：不 CPU-intensive，占内存少，但必须 responsive。

推荐 scheduling：

```text
Use pre-emptive priority scheduling, possibly combined with Round Robin within each priority level.
```

具体策略：

| Program | 特点 | 策略 |
|---|---|---|
| Editor | interactive, must be responsive | highest priority |
| Compiler | CPU + I/O, foreground task | medium priority |
| Verification | long CPU-intensive background job | lower priority |

答题句式：

```text
The editor should have the highest priority to ensure responsiveness. The compiler can have medium priority because it is useful foreground work but often blocks for I/O. The verification program should have lower priority because it is CPU-intensive and long-running. Pre-emption is needed so that the editor can interrupt the CPU-intensive task when user input arrives.
```

### 7.7 场景题：e-commerce webserver

请求类型：

1. Rendering large images：CPU expensive，可以 background。
2. Preview item list：需要快，I/O 多，CPU 少。
3. Purchase requests：CPU 少，I/O 中等，业务重要。

比较：

| Strategy | 效果 |
|---|---|
| FCFS | 大图片请求如果排前面，会拖慢 preview 和 purchase，response time 差 |
| Round Robin | 比 FCFS 公平，但不区分 purchase / preview 的重要性 |
| Priority | 最合适，可以让 purchase 和 preview 高优先级，image rendering 低优先级 |

推荐：

```text
Priority scheduling, with purchase requests highest priority, preview requests high priority, and image rendering low/background priority. Use ageing to avoid starvation of image rendering.
```

## 8. Context Switch

### 8.1 Context switch 是什么

```text
A context switch is the operation where the operating system stops running one process or thread and starts/resumes another by saving the current execution context and restoring the context of the next one.
```

中文：CPU 本来在跑 A，现在 OS 要切到 B。它必须先保存 A 的现场，再恢复 B 的现场。

### 8.2 Context switch 需要保存什么

常见步骤：

1. Trap/interrupt enters kernel mode.
2. Save current process CPU state: program counter, registers, stack pointer, status register.
3. Update process control block (PCB) of current process.
4. Choose next process using scheduler.
5. Update memory management information if needed, such as page table pointer / address space.
6. Restore next process CPU state from its PCB.
7. Return to user mode and continue executing next process.

答题模板：

```text
The OS saves the CPU state of the current process, including registers, program counter and stack pointer, into its PCB. It updates the process state, selects a new process using the scheduler, loads the new process's saved state, switches address-space information if required, and resumes execution of the new process.
```

### 8.3 为什么要避免太多 context switches

```text
Context switches are overhead because no useful user work is performed while saving and restoring process state. They may also reduce cache and TLB locality, causing the next process to suffer more cache misses. Too many context switches reduce throughput.
```

中文：

1. 保存/恢复现场本身浪费时间。
2. 切来切去会破坏 cache / TLB。
3. 真正跑用户程序的时间变少。
4. quantum 太小会导致太多 context switches。

### 8.4 但为什么不能太少

如果 context switch 太少，长任务会霸占 CPU，interactive tasks response time 差。所以 OS 要平衡：

- context switch 太多：overhead 大。
- context switch 太少：响应慢，不公平。

## 9. Paging / Segmentation / FIFO Page Replacement

### 9.1 Paging vs Segmentation

标准答案：

```text
Paging divides virtual memory into fixed-size pages and physical memory into fixed-size frames. Segmentation divides memory into variable-size logical segments such as code, stack, heap or data.
```

中文：

| Paging | Segmentation |
|---|---|
| 固定大小 pages | 可变大小 segments |
| 主要是物理内存管理方便 | 更接近程序逻辑结构 |
| page number + offset | segment number + offset |
| 可能有 internal fragmentation | 可能有 external fragmentation |

### 9.2 Swapping out 选择标准

题目常问：memory full，需要选一个 resident process swap out，怎么选以 maximize CPU utilisation 和 minimize response time？

可以答两个 criteria：

1. Swap out blocked / waiting process  
   因为它现在不需要 CPU，换出去对 CPU utilisation 影响小。

2. Swap out low-priority or background process  
   因为 interactive process 应该留在 memory 里保持 response time。

3. Swap out process with low recent activity / low working set use  
   减少马上又要 swap in 的概率。

4. Avoid swapping out I/O-active or interactive processes  
   因为会拖慢用户响应。

答题模板：

```text
A good choice is to swap out a blocked process, because it cannot use the CPU at the moment, so CPU utilisation is less likely to be reduced. Another criterion is to swap out a low-priority or background process rather than an interactive one, because this helps keep response time low for the user.
```

### 9.3 Thrashing 是什么

Thrashing 是系统大部分时间都在 page fault 和 swapping，而不是执行实际程序。

症状：

- CPU utilisation low。
- Disk activity very high。
- Page fault rate high。
- Throughput low。
- Response time high。

### 9.4 如何区分 CPU overload / thrashing / overused disk

| 原因 | 现象 |
|---|---|
| CPU overloaded | CPU utilisation high，run queue long，disk 不一定高 |
| Thrashing | page fault rate high，disk paging activity high，CPU utilisation may be low |
| Overused disk | disk utilisation high，但 page faults 不一定高，可能是 normal file I/O |

答题模板：

```text
If the CPU is overloaded, CPU utilisation and the ready queue length will be high. If the system is thrashing, the page fault rate and paging disk activity will be very high, while CPU utilisation may be low because processes wait for pages. If the disk is overused by normal I/O, disk utilisation is high but not necessarily accompanied by a high page fault rate.
```

### 9.5 FIFO page replacement 做题方法

规则：四个 frames，先来的 page 先被换掉。每次 page fault 且 frames 满了，就替换最早进入内存的 page。

做题步骤：

1. 画 4 个 frame。
2. 维护一个 queue，记录 page 进入顺序。
3. 如果 reference 已经在 frame 里：hit，不换，不改变 FIFO 顺序。
4. 如果不在 frame 且有空位：放入空位，加入 queue。
5. 如果不在 frame 且满了：换掉 queue 最前面的 page，新 page 加到 queue 后面。

示例 reference string：

```text
7, 1, 0, 3, 0, 2, 6, 4, 5, 3, 6, 2, 4, 2, 6, 1, 7, 0, 1
```

前四个通常已经给出：

```text
[7, 1, 0, 3]
```

之后按 FIFO：

| Reference | Hit/Fault | Frames after operation | FIFO order |
|---|---|---|---|
| 0 | Hit | 7 1 0 3 | 7,1,0,3 |
| 2 | Fault, replace 7 | 2 1 0 3 | 1,0,3,2 |
| 6 | Fault, replace 1 | 2 6 0 3 | 0,3,2,6 |
| 4 | Fault, replace 0 | 2 6 4 3 | 3,2,6,4 |
| 5 | Fault, replace 3 | 2 6 4 5 | 2,6,4,5 |
| 3 | Fault, replace 2 | 3 6 4 5 | 6,4,5,3 |
| 6 | Hit | 3 6 4 5 | 6,4,5,3 |
| 2 | Fault, replace 6 | 3 2 4 5 | 4,5,3,2 |
| 4 | Hit | 3 2 4 5 | 4,5,3,2 |
| 2 | Hit | 3 2 4 5 | 4,5,3,2 |
| 6 | Fault, replace 4 | 3 2 6 5 | 5,3,2,6 |
| 1 | Fault, replace 5 | 3 2 6 1 | 3,2,6,1 |
| 7 | Fault, replace 3 | 7 2 6 1 | 2,6,1,7 |
| 0 | Fault, replace 2 | 7 0 6 1 | 6,1,7,0 |
| 1 | Hit | 7 0 6 1 | 6,1,7,0 |

注意：FIFO 命中时不更新顺序，这一点和 LRU 不一样。

## 10. Kernel / System Call / Device Driver

### 10.1 System call 是什么

```text
A system call is a controlled entry point from user mode into the operating system kernel, used when a program needs services that require kernel privileges, such as I/O, process management, memory management, or accessing devices.
```

中文：用户程序不能直接碰硬件或 kernel memory，所以要通过 system call 请求 OS 帮忙。

### 10.2 `printf` / `scanf` 是否需要 system call

题目可能说：system calls only necessary for privileged resources; console printf/scanf does not require system call. True?

答案：False / not entirely true。

解释：

```text
printf() and scanf() are C library functions, but actual reading from or writing to the console requires the operating system. The library may buffer data, so not every call to printf immediately triggers a system call, but eventually console I/O is performed through system calls such as write or read.
```

中文：

- `printf` 是 library function。
- 但真正把东西写到 console，需要 OS。
- 可能有 buffering，所以不是每次 `printf` 都立刻 syscall。
- 但最终 I/O 一定绕不开 syscall。

### 10.3 User space vs kernel space

| User space | Kernel space |
|---|---|
| 普通程序运行区域 | OS kernel 运行区域 |
| 权限低 | 权限高 |
| 不能直接访问硬件 | 可以管理硬件 |
| 出错通常只影响自己 | 出错可能导致整个系统崩溃 |

### 10.4 Interrupt handler 能不能直接写 compiler process memory

一般答案：不能直接随便写。

答题思路：

```text
An interrupt handler runs in kernel context and should not directly write arbitrary data into a user process's memory. It must respect memory protection and process address spaces. The data should be copied safely using OS mechanisms, for example into kernel buffers first and then copied to the process through controlled interfaces.
```

中文：

- interrupt handler 在 kernel context。
- user process 的虚拟地址不一定在当前 context 下有效。
- 直接写会破坏 memory protection。
- 应该先放 kernel buffer，再通过安全机制 copy to user。

### 10.5 Kernel critical section 为什么要短

答题模板：

```text
Critical sections in kernel code should be short because they may block other kernel activities, increase interrupt latency, reduce system responsiveness and harm scalability on multiprocessor systems. Long kernel critical sections can delay other threads or interrupts that need the same lock.
```

中文：

1. kernel 里锁住太久会影响整个系统。
2. interrupt latency 变高。
3. 多核 scalability 变差。
4. 其他重要 kernel work 被卡住。

### 10.6 Games programmers 直接访问 graphics card 绕过 OS 的后果

稳定性：

```text
If applications bypass the OS and access hardware directly, a bug in the application or driver can corrupt device state or memory and crash the whole system.
```

安全性：

```text
It breaks protection and isolation. A malicious program could read or modify data belonging to other programs or the kernel, or misuse the hardware.
```

中文：操作系统的作用就是隔离和保护。绕过 OS 直接碰显卡，快是可能快，但安全和稳定性都炸。

### 10.7 Device driver message list 题：常见错误

看到 kernel message list code，检查：

1. `msgList` 是否可能是 `NULL`。
2. 是否为新 message node 分配内存。
3. 是否为 `message` buffer 分配内存。
4. `memcpy` 到 user space 是否安全，应该用 `copy_to_user` / `copy_from_user` 类似机制。
5. remove 时是否释放旧 node 和 message。
6. `length` 是否超过实际 message size。
7. `msgSize` 更新是否 thread-safe。
8. linked list 修改是否加锁。
9. 在 kernel 中是否用了会 sleep 的操作；如果可能 sleep，不能用 spinlock 包住。
10. critical section 是否尽量短。

### 10.8 Kernel lock：spinlock vs semaphore/mutex

| Lock | 适合 |
|---|---|
| Spinlock | 很短的 critical section，不能 sleep，中断上下文可能需要 |
| Semaphore / mutex | 可能等待较久，可能 sleep 的代码路径 |

答题句式：

```text
Use a spinlock only for very short critical sections where sleeping is not allowed, for example in interrupt context. If the operation may sleep, for example copying data between user and kernel memory or allocating memory, a semaphore or mutex should be used instead.
```

## 12. 考前速背 Answer Templates

### 12.1 Pointer

```text
A pointer is a variable storing the memory address of another object. It can be dereferenced to access or modify the object. A function can return multiple values by receiving pointer parameters and writing results through them.
```

### 12.2 Array out of bounds

```text
Array out-of-bounds access in C causes undefined behaviour. It may crash, corrupt nearby memory, produce wrong results, appear to work, or create security vulnerabilities.
```

### 12.3 Undefined behaviour

```text
Undefined behaviour means the C standard gives no guarantee about the program's behaviour. It is dangerous because the program becomes unpredictable, non-portable, hard to debug and may be miscompiled due to compiler optimisations.
```

### 12.4 Critical section

```text
A critical section is a section of code that accesses shared data and must be executed by only one thread at a time to avoid race conditions.
```

### 12.5 Race condition

```text
A race condition occurs when multiple threads access shared data concurrently, at least one access is a write, and the result depends on the timing or interleaving of the threads.
```

### 12.6 Synchronisation bugs hard to find

```text
They depend on rare timing and scheduling interleavings. They may disappear during debugging because print statements or breakpoints change the timing.
```

### 12.7 Context switch

```text
A context switch saves the state of the current process, selects another process, restores its saved state and resumes it. It is overhead because no useful user computation is performed and cache/TLB locality may be lost.
```

### 12.8 Paging vs segmentation

```text
Paging divides memory into fixed-size pages and frames, while segmentation divides memory into variable-size logical segments such as code, stack, heap and data.
```

### 12.9 Thrashing

```text
Thrashing occurs when the system spends most of its time handling page faults and swapping pages rather than executing processes. It is indicated by high page fault rate, high disk paging activity, low CPU utilisation and poor throughput.
```

### 12.10 System call

```text
A system call is a controlled mechanism for a user program to request kernel services. Console I/O through printf/scanf may be buffered by the C library, but actual reading and writing to the console ultimately requires system calls.
```

### 12.11 Kernel critical section

```text
Kernel critical sections should be short to reduce interrupt latency, improve responsiveness, avoid blocking other kernel activities and improve scalability on multiprocessor systems.
```

### 12.12 Scheduling strategy for responsive editor

```text
Use pre-emptive priority scheduling. The editor should have the highest priority to ensure responsiveness, the compiler medium priority, and the long CPU-intensive verification program lower priority. Round Robin can be used within each priority level, and ageing can prevent starvation.
```

### 12.13 Memory strategy for verification/compiler/editor scenario

```text
Use virtual memory with paging and working-set-aware replacement. Keep the editor resident because it is interactive and small. Avoid letting the large verification program cause thrashing; limit its resident set or swap out low-priority/background pages when memory pressure is high. The compiler is I/O-heavy but not memory-intensive, so it should receive enough memory for active buffers without harming editor responsiveness.
```

## 最后复习建议

优先顺序：

1. 先练 C code 找错：memory bugs + linked list + tree。
2. 再练 concurrency：shared variable、mutex、read/write lock、condition variable。
3. 再背 scheduling 场景题模板。
4. 最后练 FIFO page replacement 和 context switch / paging vs segmentation 这些稳定题。

如果时间很紧，最值得背的是：

- `free` 顺序：先保存 next / 先 free children / 最后 free 自己。
- 保护同一个 shared variable 必须用同一把 lock。
- `get()` / `handle()` 这类慢操作如果 thread-safe，应放在 lock 外最大化 parallelism。
- interactive task 用 pre-emptive priority scheduling。
- context switch 是 overhead，但太少会导致 response time 差。
